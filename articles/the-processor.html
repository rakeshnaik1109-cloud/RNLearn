The Processor: Stored Programs, Pipelines, Caches and Prediction

A processor does only simple things, such as adding two numbers or jumping to another instruction, but it does billions of them a second, guessing ahead and hiding slow memory behind clever tricks.

1. Putting It All Together

Everything so far has been a component: gates that compute, flip-flops that remember, adders that do arithmetic, memories that store. A processor combines them into a machine that does whatever a program tells it, one simple instruction at a time. The same handful of ideas, refined for seventy years, run in every phone, laptop and data centre. [1, 2]

3. The Stored-Program Computer

Early electronic computers such as ENIAC were programmed by plugging cables and setting switches. In 1945 John von Neumann, drawing on discussions with J. Presper Eckert, John Mauchly and others on the EDVAC project, described a better design: keep the program in the same memory as the data, as numbers. [3] A control unit fetches instructions one by one; an arithmetic unit executes them; memory holds both instructions and data; and input and output connect to the world. Changing the program means only writing different numbers into memory, and programs can even create or modify other programs, which is what compilers do. Maurice Wilkes’s EDSAC at Cambridge, running from 1949, was one of the first such machines in regular use.

4. Instructions and the Datapath

A processor’s instruction set architecture (ISA) is the list of operations it understands, each encoded as a binary word: load a value from memory, add two registers, store a result, jump to another instruction if a condition holds. The hardware that carries them out, the datapath, contains:

  • a program counter (PC), a register holding the address of the next instruction (a counter, Part 3);
  • a register file, a small, fast set of storage locations (flip-flops or SRAM);
  • an arithmetic logic unit (Part 2), selected by multiplexers;
  • and a control unit, a finite-state machine or decoder that turns each operation code into control signals (Part 3).

Each instruction passes through fetch (read memory at PC), decode (work out what to do), and execute (do it and update PC). The Intel 4004 of 1971 put this whole arrangement on one chip. [4] Through the 1970s instruction sets grew complex, with many addressing modes and multi-step instructions. In 1980 David Patterson and David Ditzel argued for RISC, reduced instruction set computers with simple, uniform instructions that are easy to pipeline; this philosophy underlies the ARM and RISC-V processors in phones and many other devices today. [5]

5. Pipelining

A laundry with a washer, dryer and folding table finishes loads faster if a new load starts washing as soon as the previous one moves to the dryer. A pipelined processor does the same: it splits each instruction into stages, classically fetch, decode, execute, memory access and write-back, and works on a different instruction in each stage at once. A five-stage pipeline can approach five times the throughput, with a shorter clock period because each stage does less (Part 3’s timing rule).

The complications are hazards. A data hazard occurs when an instruction needs a result that an earlier instruction has not yet written; forwarding (bypassing) routes results directly between stages, leaving only a few unavoidable stalls. A control hazard occurs at a branch, whose direction is not known until it executes; the pipeline must guess, and pay a penalty when wrong. IBM’s Stretch and Seymour Cray’s CDC 6600 of the early 1960s pioneered overlapping execution of this kind. [6]

6. The Memory Hierarchy and Caches

A modern processor core can complete an instruction in a fraction of a nanosecond, but fetching data from DRAM takes tens of nanoseconds or more: hundreds of cycles. Processor speeds improved far faster than DRAM latency for decades, a gap William Wulf and Sally McKee called the memory wall. [7] The remedy, proposed by Maurice Wilkes in 1965 as “slave memories”, is the cache: a small, fast memory that keeps copies of recently used data. [8]

Caches work because programs show locality: they reuse the same data soon (temporal locality) and use nearby addresses (spatial locality). Data moves in lines of typically 64 bytes. Modern processors have a hierarchy: small first-level caches of tens of kilobytes per core that answer in a few cycles, larger second-level caches, and a shared last-level cache of many megabytes, backed by DRAM and then storage. The average memory access time is hit time + miss rate × miss penalty, so even a small miss rate matters when the penalty is hundreds of cycles.

7. Branch Prediction and Out-of-Order Execution

Deep pipelines that fetch several instructions per cycle may have a hundred or more instructions in flight, so stalling at every branch would be ruinous. Processors therefore predict branches. In 1981 James Smith showed that simple saturating counters, which remember whether a branch was recently taken, predict well. [9] Modern predictors combine the history of many branches and are right well over 95% of the time on typical code.

The second big idea is out-of-order execution. Robert Tomasulo’s 1967 algorithm for IBM’s System/360 Model 91 let instructions wait in reservation stations and execute as soon as their operands were ready, renaming registers to remove false dependencies. [10] Today’s high-performance cores fetch, decode and retire several instructions per cycle, execute them out of order and speculatively past predicted branches, and then commit the results in program order so that the program behaves as if run one instruction at a time.

Speculation has a cost beyond complexity. In 2018 researchers disclosed the Spectre and Meltdown attacks, which trick a processor into speculatively accessing secret data; although the results are discarded, traces left in the caches can be measured. [11] Processors and operating systems have since added defences, at some cost in performance.

8. Performance: the Iron Law

The time to run a program is

time = instructions × cycles per instruction × time per cycle

The instruction count depends on the program, compiler and ISA; cycles per instruction (CPI) on the microarchitecture (pipelining, caches, prediction, superscalar issue); and the cycle time on circuits and technology (Parts 9–11). Until the mid-2000s all three improved together. Since Dennard scaling ended (Part 10), clock rates have stalled and extracting more instructions per cycle from a single thread has become ever more expensive. The industry turned instead to many cores and to specialised processors that do one kind of work very efficiently. The most important of these, the GPU, is the subject of Part 13. [1]

9. Worked Problems

Problem 1 (easy): the iron law

A program executes 2 × 109 instructions with an average CPI of 0.8 on a 4 GHz processor. How long does it take? What if a compiler reduces the instruction count by 10% but raises CPI to 0.85?

Solution

Time = 2 × 109 × 0.8 × 0.25 ns = 0.40 s. New: 1.8 × 109 × 0.85 × 0.25 ns ≈ 0.38 s, a 4% improvement. Optimising one factor while worsening another needs the full product to judge. (A CPI below 1 means the processor completes more than one instruction per cycle on average.)

Problem 2 (easy): average memory access time

A first-level cache hits in 1 cycle with a 5% miss rate. Misses go to a second-level cache (12 cycles, 20% local miss rate) and then to DRAM (200 cycles). Find the average memory access time.

Solution

Second-level average = 12 + 0.20 × 200 = 52 cycles. Overall AMAT = 1 + 0.05 × 52 = 3.6 cycles. Without the second-level cache it would be 1 + 0.05 × 200 = 11 cycles, three times worse.

Problem 3 (medium): pipeline speedup

An unpipelined processor takes 1,000 ps per instruction. It is split into 5 equal stages, with 20 ps of pipeline-register overhead per stage. Find the new cycle time and ideal speedup. If 20% of instructions are branches, 10% of which are mispredicted with a 2-cycle penalty, what is the CPI and actual speedup?

Solution

Cycle = 200 + 20 = 220 ps; ideal speedup = 1,000/220 ≈ 4.5×. CPI = 1 + 0.20 × 0.10 × 2 = 1.04, so the time per instruction is 229 ps and the speedup ≈ 4.4×. With a poor predictor (40% wrong) CPI would be 1.16 and the speedup 3.9×.

Problem 4 (medium): decoding an address

A 32 KiB direct-mapped cache has 64-byte lines, and addresses are 32 bits. How many lines does it have, and how many address bits form the offset, index and tag?

Solution

Lines = 32,768/64 = 512. Offset: log₂64 = 6 bits (byte within the line). Index: log₂512 = 9 bits (which line). Tag: 32 − 6 − 9 = 17 bits, stored with each line to check which memory block it currently holds. A 4-way set-associative cache of the same size would have 128 sets: 7 index bits and 19 tag bits.

Problem 5 (harder): predicting a loop branch

A loop runs 10 times, and is itself executed repeatedly. Its closing branch is taken 9 times and then not taken once. Compare the steady-state accuracy of a 1-bit predictor (predict what happened last time) and a 2-bit saturating counter (change prediction only after two wrong guesses in a row).

Solution

1-bit: it mispredicts the final “not taken” (it last saw “taken”), and then mispredicts the first branch of the next run (it last saw “not taken”): 2 misses in 10, 80% accuracy. 2-bit: in the strongly-taken state, the single “not taken” moves it only to weakly-taken, so the next run’s first branch is still predicted taken: 1 miss in 10, 90% accuracy. This hysteresis is why Smith’s 2-bit counters became standard.

10. Open Questions

Open questions: how much faster can one thread get?

Single-thread performance still improves each generation through wider cores, larger caches and better predictors, but the gains cost large amounts of area and power for a few percent of speed. Whether there are big untapped sources of instruction-level parallelism in ordinary programs, how to defend against speculative-execution attacks without losing performance, and whether open instruction sets such as RISC-V will reshape the industry are actively debated. Hennessy and Patterson have argued that the next big gains will come from domain-specific architectures and languages rather than general-purpose cores. [1]

12. Myth vs Reality

Myth vs Reality: “processors run instructions one after another”

The myth: a CPU reads an instruction, does it, then reads the next.

The reality: that is the illusion the hardware preserves. Internally, a modern core has hundreds of instructions in flight, executes them out of order and speculatively along predicted paths, and throws away work when a guess was wrong, then presents results as if everything ran in order. The gap between the simple model and the real machine is the source of both its speed and of attacks such as Spectre.

Why it matters: programmers can rely on the simple model for correctness, but performance and security depend on the hidden machinery.

13. Key Takeaways

Key takeaways
  • A stored-program computer keeps instructions and data in the same memory; a program counter steps through the instructions.
  • The datapath combines a register file, an ALU, multiplexers and a control state machine; each instruction is fetched, decoded and executed.
  • Pipelining overlaps instructions; forwarding and branch prediction reduce the stalls caused by hazards.
  • Caches exploit locality to hide slow DRAM; AMAT = hit time + miss rate × miss penalty.
  • Out-of-order, speculative execution finds parallelism in ordinary programs, at a cost in complexity and security.
  • Time = instructions × CPI × cycle time; since clock rates stalled, gains come from parallelism and specialisation.
